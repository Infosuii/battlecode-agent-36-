## Cached identity and action/fuel interaction

Reviewed source hashes: draft.cpp `73527394a0f8ea5081d7691e7d351307d4ace1ca0c9f3b4a658a1b3946f3903d`; draft_map_cache.h `6211b9cdb09896f93b69c486381ebab379795e930dc258ed503fb717a7a38300`; strategy.h `6aa5144bd5f659932ca8f354ad1e52dc7fad74170db0bd922b14adf9d9ce55fc`.

The design avoids the earlier expensive game-phase exact-map scan. Draft uses the full immutable layout comparison, caches its result per module and records it in the owning team's draft memory. Game phase only checks the startup snapshot, version/length/context/CRC, then the cheap descriptor. Invalid or missing records become unknown permanently in that module; there is no permissive descriptor fallback and no game-phase full scan. A known descriptor alone cannot grant exact identity.

SDK semantics were inspected directly: draft_memory is an immutable startup snapshot. Assignment submits bytes to the engine but does not update that captured snapshot, and short writes retain the remaining engine bytes. The writer handles these semantics correctly by constructing a new 16-byte array on every draft write, keeping the original six prefix bytes' meaning and explicitly zeroing extension bytes 6–15 if helper encoding fails. It does not attempt to read back its own submission through the stale snapshot. The checksum includes prefix 0–5 and context fields, while encoding leaves that prefix unchanged. There is one SDK writer (brain::record_draft); the identity helper only fills its supplied array. This is separate from gameplay shared claim memory.

No move, attack, cast or channel allowance is consumed by the new cache reader/writer. The per-game path is bounded small-array/CRC work with cached return on subsequent calls. Draft-only canonical work still consumes real draft fuel. This is not a whole-game fuel governor guarantee: initialization, observation, action/tail work, and unrelated planners can still suspend. The current config has APEX_BRAIN=1, needed for its existing writer; BRAIN=0 would fail closed to unknown rather than populate the record. Short capacities use the existing 4/5/6-byte writer and the cache reader rejects missing extension safely.

## Fresh protocol review

The first fresh_validation.py text had material ambiguities: undefined material outside-map regression, unclear negative-pool metric, undefined exhaustion comparison/denominator, no explicit shift/baseline stack gate, protocol overwrite on resume and loose existing-schedule reuse. These were reported before fresh games.

Reviewed replacement tools/fresh_protocol.py v2 resolves the substantive numeric selection rules:

- Rows prerequisites include native cache/writer checks, OFF parity and nonnegative isolated outside-rows official point/gem outcomes. Fresh pool points AND gems versus baseline must be nonnegative. Fresh and shift head comparisons each require at least 50% points and nonnegative gem margin.
- Governor can be selected only if rows passes. It requires nonnegative pool point/gem effects against both rows and baseline, head/shift gates, and strictly fewer total native exhaustion entries than rows over the identical 160-game pool. Equality fails the exhaustion condition.
- Fault rejection, deterministic tie handling, fixed baseline/rows/stack fallback and one selection before final holdout are specified. These are point-based rules, not significance claims or non-inferiority proof.
- Protocol captures build hashes and map hashes and refuses a changed protocol. All schedules are frozen before execution; a receipt captures protocol and schedule hashes. The old executable entry delegates to the reviewed version.

Re-review confirms the earlier mechanical recommendations are implemented: expected 40/10 validation map counts, the exact required map/opponent/side job grid with unique IDs, and immutable receipt verification. fresh_validation.py is now only a compatibility import of the reviewed main function, eliminating the old alternate entry path. Final selection must still record each actual numeric gate from complete receipts, including zero-fault checks across every relevant candidate schedule. A candidate must not pass through a missing, partial or unmatched schedule.

## Exact release review checklist

1. **Selection and identity.** Record frozen selection receipt, selected development artifact/source hash, fresh gate values and all active macros. Recompute source tree and selected artifact hash against the original build manifest before copying. Do not silently package modified experiment files.
2. **Packaged defaults.** Selected ON/OFF values must be materialized in source. Build without experimental command-line -D values and verify every requested default in the preprocessor receipt. Keep diagnostics/exhaustive research flags off and baseline intended search/model flags explicit. Compiler options, SDK/CLI and release mode are recorded.
3. **Selection versus exact build.** Materializing defaults can alter optimizer layout/fuel even if preprocessor values match. Compare development-selected behavior with the exact source-default artifact, and perform final evaluation on the latter. If binary hashes differ, do not identify them as one artifact without behavioral evidence.
4. **Archive equality and rebuild.** Use the legal local bundler, inspect actual archive layout, compare extracted source tree with the frozen materialized source, and rebuild extracted files using no extra experiment flags. The rebuilt binary must match the exact release hash. The current helper assumes a src/ folder under the extracted bot; confirm actual bundler layout or make discovery explicit.
5. **Frozen baseline fallback.** package_release.py's generic default-replacement loop requires exactly one #define placeholder for every new switch. Frozen 18-file baseline has no new-switch placeholders; selecting baseline needs its dedicated unchanged-source package path, or an explicit choice of a tested all-OFF candidate with separate identity. Do not mutate the frozen baseline to make the generic helper work.
6. **Exact-artifact evidence.** Freeze artifact/hash before final primary and structural-shift holdout. Validate necessary interactions and important leave-one-out comparisons, engine identity, completed full-length semantics, native faults/exhaustion and the protocol's selection limits. No post-holdout policy tuning under the same pristine label.
7. **Rollback and provenance.** Preserve the immutable 18 baseline files and baseline WASM/hash, legal source archive, build entry point, switch manifest, uncertainty, rejected variants and known residual suspensions/model gaps. Distinguish the selected candidate, source-default rebuild, instrumented diagnostics, baseline and platform version.
8. **Local versus publication.** Local packaging does not establish live submission or ladder gain. GitHub writes remain blocked by the reported automatic review; pending publication records stay local until the required final approval. No alternate publication route.
